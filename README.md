# Predictive Maintenance Platform (PMP)

PMP learns the normal behaviour of plant equipment from sensor data, compares live values with that behaviour, and turns the difference into a Deviation Index and a 0–100 Health Score. It raises managed alerts before fixed alarm limits are reached, explains which sensors and failure modes are involved, forecasts time to a limit, and carries the response through a case to a recorded outcome.

Architecture: a modular monolith (Python back end, React front end, PostgreSQL with TimescaleDB), one container image running a web role and a worker role. The specification pack is PMP-PRD-001, PMP-UCS-001, PMP-PDS-001, PMP-ARC-001 and PMP-GAP-001 (Rev A). Build progress follows [`docs/implementation-plan.md`](docs/implementation-plan.md).

## Getting started

Docker Desktop must be running.

```
cd backend
uv sync                      # creates backend/.venv with Python 3.12 and all tools
cp .env.example .env         # local settings (never committed)
cd ..
make db-up                   # PostgreSQL 16 + TimescaleDB on localhost:5433
make check                   # lint, format, types, import contracts, unit + integration tests
```

| Command | What it does |
| --- | --- |
| `make check-unit` | All checks except the integration tests (no database needed) |
| `make format` | Apply Ruff formatting and safe lint fixes |
| `make migrate` | Upgrade the dev database to the latest migration |
| `make web` | Run the web role on http://127.0.0.1:8000 (`/healthz`, `/api/v1/docs`) |
| `make worker` | Run the worker role (job queue) |
| `make db-down` / `make db-reset` | Stop the database / wipe and restart it |

## Loading the demo plant

The registry (assets, tags, asset types and roles) can be imported from one Excel workbook
or from CSV files named after its sheets (`asset_types`, `roles`, `assets`, `tags`).
Files are validated first; any problem is reported with its line number and nothing is
written. Re-importing the same file changes nothing.

```
make db-up && make migrate
cd backend
uv run pmp registry import ../data/demo/registry/registry.xlsx --dry-run   # validate only
uv run pmp registry import ../data/demo/registry/registry.xlsx
```

The demo files are generated by `backend/tools/build_demo_registry.py`.

## Sending live data (gateway ingestion)

The OT gateway posts batches to `POST /api/v1/ingest/samples` with an API key of scope
`ingest` (PMP-ARC-001 §7.1.1). Keys are shown once and stored only as a hash.

```
cd backend
uv run pmp apikey create --name "Site A gateway" --scope ingest   # copy the key now
uv run pmp apikey list
uv run pmp apikey rotate <id>     # replacement key; revoke the old one after switching
uv run pmp apikey revoke <id>
```

Interactive API documentation: http://127.0.0.1:8000/api/v1/docs (`make web`).

## Loading history

History files (CSV or Parquet; long format `ts, tag, value, quality` or wide format `ts`
plus one column per tag) load through `POST /api/v1/ingest/backfill`, which queues a job
for the worker, or directly from the command line. Every row is checked; counts always
reconcile (rows read = loaded + duplicates + rejected). Timestamps need a UTC offset
unless `--naive-as-utc` is given.

```
cd backend
uv run pmp ingest backfill history.parquet --source gw-site-a-01 --preview   # check first
uv run pmp ingest backfill history.parquet --source gw-site-a-01             # skip overlaps
uv run pmp ingest backfill history.parquet --source gw-site-a-01 --mode overwrite
```

Over HTTP: upload with `preview=true`, read the result from `GET /api/v1/jobs/{id}`, then
`POST /api/v1/ingest/backfill/{upload_id}/load`. The worker (`make worker`) runs the jobs.

`make perf-backfill` runs the FR-ING-03 acceptance check: 12 months of 1-minute data for 50
tags (about 26 million samples).

## Data-quality rules

Every scoring cycle, each sensor goes through the UCS §6.1 rules in order and the first match
sets its NAMUR NE 107 status: bad quality and stale (Failure), manual exclusion (Function
check), out of instrument range (Out of specification), flatline, spike and uncertain quality
(Maintenance required), otherwise Good. Defaults can be overridden globally, per asset-type
role or per tag; each save is a new, audited version and applies from the next cycle. Saving
previews the effect on the last 30 days first and refuses if a tag would be excluded more
than 20 % of the time, unless `--yes` is given.

```
cd backend
uv run pmp dq preview                                     # effect of the current rules
uv run pmp dq preview --tag K101.TI1018.PV spike_pct=30   # effect of a change, not saved
uv run pmp dq set --tag K101.SI1001.PV flatline_used=on --comment "constant-speed machine"
uv run pmp dq set --role centrifugal_pump/flow stale_factor=5
uv run pmp dq show --tag K101.SI1001.PV                   # overrides, history, effective values
uv run pmp dq status --asset K-101                        # evaluate now and list statuses
```

`NAME=default` removes an override. Parameter names: `pmp dq set --help`.

## Prediction algorithms (detectors)

Every normal-behaviour model implements the Detector contract in
`backend/pmp/modelling/algorithms/contract.py` (PMP-ARC-001 §8.1). Third-party algorithms are
installed Python packages registered under the `pmp.algorithms` entry point, never uploaded
code (ADR-09). Each detector found runs the contract suite (output shape, missing inputs,
save and load, determinism, refusing bad input) and is used only if it passes.

```
cd backend
uv run pmp algorithms list
```

Until the AAKR model arrives (Phase 7), the default detector is a placeholder that predicts
each sensor as its training median. **Scores made with it are for demonstration only.**

## Scoring outputs

Each cycle turns actual and predicted values into the outputs of PMP-UCS-001 §6.2 and §6.5:
residual, relative deviation q, standardised residual z, the Deviation Index, contributions,
the Health Score, the band and coverage (`backend/pmp/scoring/outputs.py`). The AC-03
reference set in `backend/tests/reference_data/` checks every output to 1e-6; its expected
values come from `backend/tools/build_scoring_reference.py`, which uses exact decimal
arithmetic and is independent of the scoring code. Regenerate it only when a case is added:

```
cd backend
uv run python tools/build_scoring_reference.py
```

## Model definitions

A model monitors one asset: its sensors (some marked required), one or more training periods,
a hold-out validation period that may not overlap them, operating-mode filters and alert
rules (PMP-UCS-001 UC-05, §6.6). Until the model builder screens arrive (Phase 6), models are
defined from a JSON file; times can be ISO 8601 or relative (`-60d` is 60 days before today
00:00 UTC). Filters compare tags (by source name) with numbers, e.g. `K101.II1001.PV > 120`,
combined with `and`, `or`, `not` and brackets; they are parsed safely, never executed.

```
cd backend
uv run pmp model create ../data/demo/models/k101.json   # create, or update the draft
uv run pmp model show K-101 main
uv run pmp model list
uv run pmp model train K-101 main --now   # train here; without --now a job for `make worker`
```

Training lays the chosen periods on the model's 60 s cycle grid exactly as scoring will
(sample-and-hold, data-quality rules, operating-mode filter), blocks with a plain reason if
fewer than 2,000 cycles or under half the period remain, fits the detector, plays the model
back over the validation period and writes the artefact folder
(`<PMP_ARTEFACT_DIR>/models/<model>/<version>/`: algorithm files, `scaling.json`,
`manifest.json`, `validation.json`) with its SHA-256. The version ends Validated, or Failed
with the reason; saving the definition again moves a Failed version back to Draft.

## Demo plant data (synthetic)

A deterministic simulator of the demo plant (`pmp.demo`) produces realistic 1-minute data
for every registered tag: sensors on one machine move together with its load, there are
turndowns and monthly trips, and the wireframe fault story is built in (K-101 thrust-bearing
degradation, flatlines, a stale tag, a lost gateway link, an out-of-range pressure, spikes,
occasional Bad quality). The story is timed from an anchor day (default: today, UTC).
Same seed, same data. **Synthetic: it proves the software, not detection on real equipment
(that is AC-04, which needs the client's history).**

```
make db-up && make migrate
cd backend
uv run pmp registry import ../data/demo/registry/registry.xlsx
uv run pmp demo history                       # 180 days through the history import
uv run pmp apikey create --name "Demo gateway" --scope ingest
uv run pmp demo replay --key <key> --from -2h # catch up 2 h quickly, then live every minute
```

## Running the full stack in containers

One image runs both roles (`pmp web`, `pmp worker`). To run database, web and worker together:

```
cp deploy/.env.example deploy/.env   # once
make up                              # builds the image and starts everything
curl http://127.0.0.1:8000/healthz
make logs                            # follow the logs; Ctrl+C to stop following
make down
```

`make image` builds the image on its own (`pmp:local`).

## Continuous integration

GitHub Actions (`.github/workflows/ci.yml`) runs on every push and pull request:
lint, format check, type check, import contracts, unit and integration tests against a
TimescaleDB service container, the 80% coverage gate on the analytics modules, a
dependency audit (`make audit`), then builds the image and smoke-tests `/healthz`.

## Module boundaries

Back-end modules talk to each other only through each module's public `__init__.py` (PMP-ARC-001 §4.1). The rules are enforced with import-linter (`make contracts`) and run in CI:

- `core` is the bottom layer and imports no feature module.
- Feature modules (ingestion, registry, dataquality, modelling, scoring, alerting, diagnostics, prognostics, advisory, cases, notifications, reporting) may use each other's public interfaces only.
- `api` sits on top; nothing imports it.
