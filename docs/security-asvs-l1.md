# OWASP ASVS 4.0.3 level 1 review (NFR-SEC, ARC §9, plan 9.2)

How PMP meets the level 1 requirements that apply to it, chapter by chapter, as of
2 November 2026. "Not applicable" means PMP has no such feature. One requirement is not
met (2.1.7), with the reason and the compensating controls. Two gaps found in this review
were fixed in 9.2: passwords over 128 characters are now refused (2.1.2), and API
responses carry `Cache-Control: no-store` (8.2.1). The session cookie also gained the
`__Host-` prefix over HTTPS (3.4.4).

| Chapter | Status | How it is met (evidence) |
| ------- | ------ | ------------------------ |
| V1 Architecture | Met | Level 1 has no testable items. The design is documented in ARC-001; trust boundaries are the proxy, the API key scopes and the role matrix (ARC §9). |
| V2 Authentication | Met, except 2.1.7 | Passwords 12 to 128 characters, any characters, no composition rules, not containing the username (2.1.1–2.1.9, `pmp/core/users.py`, `tests/unit/test_passwords.py`); Argon2id hashing (2.4); the same message for unknown user, wrong password and locked account, and 5 failures lock an account for 15 minutes (2.2.1); users change their own password with the current one (2.1.5); administrators reset others' and every session of that user ends. API keys are 256-bit random, shown once, stored as SHA-256, scoped (ingest or results-read), revocable and rotatable (2.10). |
| 2.1.7 breached passwords | **Not met** | The host is offline from the internet by design (NFR-SEC-02), so no breach service can be queried, and no breached-password list ships with the image. Compensating: 12-character minimum, lockout after 5 failures, sign-in only from the plant network through the proxy. Possible later step: ship a list of the most common passwords and refuse those. |
| V3 Session management | Met | Session tokens are 256-bit random, stored as SHA-256 (3.2); idle timeout 30 minutes, absolute 12 hours, ended on sign-out, deactivation and password reset (3.3); cookie `HttpOnly`, `Secure`, `SameSite=Lax`, `__Host-` prefixed over HTTPS (3.4, `tests/integration/test_users.py`); changes through the cookie need the session's CSRF token (3.5, 4.2.2). Tokens are never in URLs. |
| V4 Access control | Met | Every operation checks the ARC §9.2 role matrix and the user's scope in the hierarchy on the server, before any existence check (4.1, 4.2, decision 6.7); roles are read on every request so changes apply at once. `tests/integration/test_api_contract.py` replays every change as every refused role (AC-07). Administrative screens are also hidden from other roles, but the server check is what counts. |
| V5 Validation, sanitisation, encoding | Met | Every request body and parameter is validated by Pydantic schemas with types, lengths and ranges; unknown fields are refused on the ingest schema (5.1). SQL uses bound parameters only (5.3.4). The front end is React, which escapes output; there is no `dangerouslySetInnerHTML` (5.3.3). No XML, no templates rendered from user input. Model artefacts are the only serialised objects loaded, written by PMP's own training and checked against the SHA-256 stored with the version before loading (5.5). |
| V6 Stored cryptography | Met | Python's `secrets` for tokens, keys and CSRF values (6.3); Argon2id for passwords, SHA-256 only for random secrets (6.2); no custom cryptography. |
| V7 Error handling and logging | Met | Errors return RFC 7807 problem details; unexpected ones say "Internal error" and nothing more, the detail goes to the log (7.4). Structured JSON logs with request ID and user (ARC §10.3); sign-ins, failures, lockouts, CSRF refusals and API key use go to the `pmp.security` log; secrets are `SecretStr` and never logged (7.1). Every administrative change is in the audit trail (FR-AUD-01). |
| V8 Data protection | Met | API responses are `Cache-Control: no-store` (8.2.1); no sensitive data in URLs; the browser stores only remembered filters, never tokens (8.2.2); data retention is configurable (NFR-DATA-01). |
| V9 Communications | Met | TLS at the Caddy proxy (TLS 1.2 and 1.3 only, HTTP redirected to HTTPS, HSTS), certificates from the corporate CA (9.1, `deploy/Caddyfile`). The SMTP relay uses STARTTLS on 587. |
| V10 Malicious code | Met | No dynamic code loading from users; dependencies pinned by lock files; `make audit`, `make fe-audit` and the image scan (`make scan`, Trivy, fails on a fixable critical) run in CI; an SBOM is produced for every build (10.3). |
| V11 Business logic | Met | Sequential steps are enforced on the server (model lifecycle, case states, alert transitions); ingestion is rate limited per key (11.1.4); history imports are size limited. |
| V12 Files and resources | Met | History uploads: `.csv` and `.parquet` only, at most `PMP_BACKFILL_MAX_MB`, stored under a random name outside the served files, never executed (12.1, 12.3, 12.4). Downloads (audit CSV) are generated, not user paths. No server-side fetches of user URLs (12.6). |
| V13 API | Met | Authentication on every API operation except sign-in, health and the internal `/metrics` (blocked at the proxy); content types checked; batch size and body size limits (13.1–13.2). The OpenAPI document matches the API, checked in CI. |
| V14 Configuration | Met | Configuration from environment variables, secrets in `deploy/.env` never committed (14.1); the image runs as a non-root user (14.1.5); security headers on every response: CSP, `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, HSTS (14.4); the `Server` header is removed at the proxy. The interactive API documentation (`/api/v1/docs`) is readable without signing in: it describes the API but grants nothing, and it is exempt from the CSP because Swagger UI loads its own scripts. |
